# Аудиозвонки iOS — архитектура и история фиксов

Статус: **голосовые звонки подтверждены стабильными** (пользователь, целый день тестирования на реальных устройствах, 2026-08-05). Документ описывает финальную архитектуру аудио-стека и путь к ней — от первых проблем с холодным стартом до кастомного `RTCAudioDevice`.

Известные незакрытые пункты (не блокируют текущий статус, отдельные задачи на будущее): нет ручного выбора Bluetooth-маршрута из своего UI (только из нативного экрана CallKit) — см. конец документа. (Экран гаснет на видеозвонках — исправлено; звонок "сам отключался" в редких случаях — исправлено; оба см. там же.)

## Архитектура (текущее состояние)

Три файла отвечают за звонок:

- **`Call/CallManager.swift`** — оркестрация: состояние звонка, CallKit (`CXProvider`/`CXProviderDelegate`), сигнализация через протокол Nevod (`vcall:offer/answer/ice/ring/reject/hangup/busy`), WebRTC `RTCPeerConnection`, UI-состояние кнопки "Динамик".
- **`Call/NevodAudioDevice.swift`** — весь физический звук: захват микрофона, воспроизведение, эхоподавление, владение `AVAudioSession`. Полностью заменяет встроенный Audio Device Module (ADM) WebRTC.
- **`Views/CallOverlay.swift`** — собственный SwiftUI-экран звонка (виден только когда приложение на переднем плане).

Ключевое архитектурное решение: **WebRTC не управляет `AVAudioSession` вообще**. Раньше (до билда 76) WebRTC делал это сам через свой встроенный `RTCAudioSession`, и именно это стало корнем самой долгой проблемы этого раунда (см. ниже). Сейчас `RTCPeerConnectionFactory` создаётся с явным кастомным аудио-устройством:

```swift
private static let audioDevice = NevodAudioDevice()
private static let factory: RTCPeerConnectionFactory = {
    RTCInitializeSSL()
    return RTCPeerConnectionFactory(
        encoderFactory: RTCDefaultVideoEncoderFactory(),
        decoderFactory: RTCDefaultVideoDecoderFactory(),
        audioDevice: audioDevice
    )
}()
```

`NevodAudioDevice` реализует публичный протокол WebRTC `RTCAudioDevice` (`WebRTC/RTCAudioDevice.h`) — задокументированный, официальный extension point именно для такой замены, не хак. Устройство собирает звук через `AVAudioEngine` с `setVoiceProcessingEnabled(true)` (даёт то же бесплатное эхоподавление/AGC/NS, что и встроенный ADM), `AVAudioSourceNode`/`AVAudioSinkNode` для playout/recording. Сама категория/активация `AVAudioSession` настраивается **один раз** внутри `NevodAudioDevice.activateSession()`, реакция на смену маршрута — только по факту изменения реального формата железа (sample rate/каналы), никогда не слепым переприменением `setCategory`.

Архитектура написана по образцу референсной реализации, на которую прямо ссылается сам заголовок `RTCAudioDevice.h` — `github.com/mstyura/RTCAudioDevice` (`AVAudioEngineRTCAudioDevice.swift`), урезанной под голосовые звонки (без микширования фоновой музыки).

## История: путь к этой архитектуре

### Этап 1 — холодный старт и первичная активация звука (билды до ~68)

Первые баги были не про маршрут, а про то, что звук вообще не включался при входящем звонке с холодного старта (VoIP push):

- `AVAudioSession.setActive(true)` иногда падает с `NSOSStatusErrorDomain 561017449 "Session activation failed"`, если CallKit ещё сам в процессе активации сразу после `reportNewIncomingCall`/`CXAnswerCallAction` — решено ретраем с задержкой.
- CallKit не гарантирует вызов `didActivate` для каждого звонка (пропускает, если считает сессию уже активной от предыдущего звонка в том же процессе) — код должен сам инициировать активацию, не полагаясь только на этот колбэк.
- Отдельный, более упрямый случай (`1701737535`, а не `561017449`) — сессия могла оставаться в непонятном состоянии по 7+ секунд. Фикс — "толчок" через `CXProvider.reportCall(with:updated:)`: любой CXProvider-апдейт (даже не связанный с аудио напрямую) иногда выводил CallKit из залипшего состояния.

### Этап 2 — устойчивость соединения (2026-08-03)

Формально не аудио-баг, но маскировался под "звонок не работает": `NevdClient.isConnected` считал соединение живым, пока не падало явное чтение из сокета, а тихо умерший TCP-сокет мог не подавать признаков жизни сколь угодно долго. Фикс — TCP keepalive через `NWProtocolTCP.Options` (официальный механизм Apple `Network.framework`), а не самодельный ping/pong.

### Этап 3 — кнопка "Динамик" (билды 68-75, самый долгий раунд)

Симптомы менялись от билда к билду — кнопка залипала на громкой, гасла сама через 2-3 сек, срабатывала только со второго нажатия, — но все были проявлениями одной и той же группы причин:

1. **`isSpeaker` принудительно форсировался в `true`** при каждом повторном входе в функцию активации звука (а она вызывается много раз за звонок) — любой выбор пользователя тихо перезаписывался обратно. Убрано принудительное присваивание.
2. **Модель "enforce" вместо "sync"**: код пытался силой удерживать реальный маршрут в соответствии с `isSpeaker`, реагируя на любую смену маршрута. Это ломало легитимный сценарий — когда собственный экран `CallOverlay` не на переднем плане (см. ниже), единственный способ управлять звуком — нативная кнопка CallKit, и "enforce"-логика откатывала выбор пользователя за миллисекунды, принимая его за помеху. Переписано на "sync" — пассивно отражать `isSpeaker` в соответствии с реальностью, никогда не бороться с внешними изменениями.
3. **Настоящий корень (билд 74)**: `activateAudioSessionAsync()` может вызываться повторно за один звонок (повторное срабатывание `didActivate` у CallKit — ожидаемый случай). Каждый повторный вызов заново гонял `setCategory()` — а это не безобидный no-op: переприменение категории тихо сбрасывает активный `overrideOutputAudioPort` обратно на дефолт. Узкий гард (`categoryConfigured`) вокруг именно `setCategory` (не всей функции) решил и пропажу звука, и залипание кнопки — но **только на собственном экране `CallOverlay`**.

### Платформенное ограничение: нативный экран CallKit

Отдельная, независимо подтверждённая проблема: ответ на звонок с холодного старта/lock screen **не выводит собственный UI приложения на передний план** — это подтверждённое ограничение iOS для VoIP-приложений (проверено два разных API — `UIApplication.shared.open(...)` с кастомной URL-схемой и `requestSceneSessionActivation`, оба не сработали; пользователь независимо проверил Телеграм на том же сценарии — то же самое). В этом состоянии виден **нативный экран CallKit** со своей собственной кнопкой "Динамик", не связанной с нашим кодом никак, кроме общего `AVAudioSession`.

### Этап 4 — самопроизвольное переключение на нативном экране (билды 75-76)

После фикса категории на `CallOverlay`, на нативном экране CallKit маршрут продолжал сам скакать между "ухо"/"громкая" каждые несколько секунд. Последовательно исключено:

- Версия WebRTC (M149 → M150) — идентичное поведение.
- Bluetooth (сопряжённые, но не подключённые устройства) — выключили полностью, идентичное поведение.
- Чистая iOS/proximity-эвристика — Telegram в тех же условиях (телефон в руке, экраном вверх, не у уха) такого не показывает.

**Найденный корень**: встроенный в бинарник WebRTC класс `RTCAudioSession` сам подписан на `AVAudioSessionRouteChangeNotification` и при любой смене маршрута заново вызывает `setCategory()` **изнутри фреймворка** — невидимо и неотключаемо нашим кодом (нет публичного флага, подтверждено по официальному заголовку `RTCAudioSession.h`; подтверждающий прецедент — GitHub issue `livekit/client-sdk-swift#391`, описывающий идентичный симптом). Пересборка WebRTC из исходников с патчем не рассматривалась как решение — это дало бы тот же самый код Google (баг не специфичен для конкретной сборки), а форк с собственным патчем означал бы вечную поддержку при каждом апдейте.

**Решение** — кастомный `RTCAudioDevice` (см. "Архитектура" выше), полностью убирающий встроенный ADM WebRTC из цепочки, а вместе с ним и его недокументированное внутреннее поведение.

**Методологическая ловушка при проверке фикса**: анализ логов после установки билда 76 поначалу выглядел так, будто дрейф продолжается (`routeChange fired reason=3/4` чередование). Это оказалось ложной тревогой — нажатие на нативную кнопку CallKit никогда не проходит через нашу функцию `toggleSpeaker()`, значит отсутствие записи об этом вызове в логе **не доказывает**, что никто не нажимал кнопку. Только прямое ручное тестирование пользователем (нажатия посреди разговора, намеренное ожидание без нажатий) via сравнение с поведением Telegram сняло вопрос.

### Этап 5 — краш при ответе на звонок: гонка потоков вокруг AVAudioEngine (2026-08-08)

После добавления обработчика `AVAudioSessionRouteChangeNotification` (см. выше, фикс Bluetooth) одна из сторон звонка стала случайным образом падать через несколько секунд после ответа — воспроизводимо, но непредсказуемо какая именно сторона.

**Диагностика по реальным краш-логам с устройства** (Xcode → Devices and Simulators → View Device Logs, `Nevod-*.ips`, не `Analytics-*.ips` — последние оказались общей ежедневной телеметрией устройства, не имеющей отношения к приложению):

```
*** Terminating app due to uncaught exception 'com.apple.coreaudio.avfaudio', reason:
'required condition is false: nil == owningEngine || GetEngine() == owningEngine'
```
на `newEngine.attach(passThroughNode)` в `updateEngine()`.

**Причина — гонка данных, в два слоя:**

1. `passThroughNode` — единственный persistent-инстанс `AVAudioMixerNode`, переиспользуемый при каждой пересборке `AVAudioEngine` (в отличие от `audioSinkNode`/`audioSourceNode`, создаваемых заново). `shutdownEngine()` открепляла от старого engine только эти два, но не `passThroughNode` — при повторной пересборке `attach()` падал, т.к. нода всё ещё "принадлежала" уже остановленному engine.
2. **Более глубокая причина**: `updateEngine()` вызывалась из двух несинхронизированных контекстов одновременно. Все "внутренние" вызовы (interruption/routeChange/engineConfigChange-уведомления, `activateSession()`) шли через `queue.async` (serial `DispatchQueue`) — сериализованы между собой. А вот `startPlayout()`/`stopPlayout()`/`startRecording()`/`stopRecording()`/`terminateDevice()` — методы протокола `RTCAudioDevice`, вызываемые WebRTC с его собственного внутреннего потока — вызывали `updateEngine()` **напрямую, синхронно**, минуя `queue` полностью. Новый route-change-обработчик резко увеличил частоту вызовов `updateEngine()` именно в первые волатильные секунды после ответа (когда WebRTC тоже активно дёргает `startPlayout`/`startRecording`) — отсюда и рост вероятности реального пересечения по времени.

**Фикс (двухчастный, оба нужны)**:
- `shutdownEngine()` теперь дополнительно открепляет `passThroughNode` — корректно и для последовательных (не гоночных) пересборок.
- Все точки входа `RTCAudioDevice` (`startPlayout`/`stopPlayout`/`startRecording`/`stopRecording`/`terminateDevice`) переведены на `queue.async`, как и всё остальное в классе, включая запись `shouldPlay`/`shouldRecord` (обычные `var`, не `AtomicBool` — тоже были уязвимы к гонке, раз читаются только внутри `updateEngine()`).

Подтверждено на реальных устройствах: тот же всплеск `setActive FAILED` (код `1701737535`, известный сценарий) происходит и теперь, но звонок больше не падает — доходит до видео, кадры идут в обе стороны, завершается штатно по `hangup`. Закоммичено `dac3c95`.

**Урок на будущее**: `RTCAudioDevice`-протокольные методы вызываются WebRTC с ЕГО СОБСТВЕННОГО потока, не с того, что вызвал `activateSession()`/остальной публичный API класса — при добавлении новой мутирующей логики в `NevodAudioDevice` всегда проверять, что путь идёт через `queue`, а не полагаться на "и так было синхронно, значит безопасно".

### Этап 6 — звонок "сам отключался" на редком стечении обстоятельств: CXEndCallAction не проверял callUUID (2026-08-11)

Пользователь сообщил: холодный старт на Б, первый звонок — в момент ответа Б звонок у А сам обрывается; второй звонок в тех же условиях проходит нормально. Первая гипотеза была про Bluetooth (у Б была подключена гарнитура) — **опровергнута тремя контрольными прогонами** (см. ниже): без Bluetooth баг тоже воспроизводился при нестабильном сокете у А, а с Bluetooth (включая видео) звонки проходили чисто, когда сокет у А был стабилен. Диагностировано только по парным логам с обеих сторон (`nlog`) — без них было невозможно отличить "Б сам отклонил" от "что-то на А сломалось".

**Реальная причина, найдена по логам:**
1. У А в момент набора сокет к ноде оказался не подключён (`sendCallOffer SKIP not connected`). Встроенная self-healing логика (`CallManager.watchForStaleConnection`, через 5с без "ring") форсирует переподключение и повторно вызывает `dial()` — из-за чего на ноду фактически ушло **два разных `vcall_offer`-пакета** от одного и того же звонка.
2. Каждый буферизованный `VCALL_OFFER` независимо триггерит свой VoIP-push (`node/router.py`) — на Б пришли **два** VoIP-push почти одновременно (видно как два `NevdApp:102 voip push received` подряд с разницей в 1мс).
3. `CallManager.reportIncomingCallFromPush()` обязан репортить в CallKit КАЖДЫЙ push (контракт Apple) — второй, дублирующий push репортится как отдельный, служебный `CXCall` и тут же завершается через `CXEndCallAction`, поскольку `state` уже не idle (занято первым, настоящим звонком).
4. **Баг**: `provider(_:perform: CXEndCallAction)` реагировал на завершение ЛЮБОГО `CXCall`, не проверяя `action.callUUID` — он читал/писал только общие `self.state`/`self.callUUID`/`self.hangupSent`. Завершение служебного дубля срабатывало против состояния настоящего, ещё звонящего звонка — тот получал `vcall:reject`, будто его отклонили, хотя пользователь Б ничего не нажимал.

**Фикс** (`CallManager.swift:1416-1441`, коммит `9ee8708`): одна строка-guard `guard action.callUUID == self.callUUID else { return }` в начале обработчика — завершение чужого/служебного `CXCall` больше не трогает состояние отслеживаемого звонка. Безопасно и для обычного пути `hangup()`/`reject()` (они сами шлют сигнал и сами вызывают `reset()` до того, как этот делегат асинхронно долетит — `reset()` идемпотентен, `logCall()`/`state.cellId`-guard'ы уже не дают продублировать эффект).

**Контрольные тесты, которыми опровергли Bluetooth-гипотезу**:
- Без Bluetooth, но с нестабильным сокетом у А (как в первом отчёте) — баг воспроизводился.
- Без Bluetooth, сокет у А стабилен — 2 звонка подряд чисто, без единого лишнего push.
- **С Bluetooth**, сокет у А стабилен — 2 звонка подряд чисто, включая видео, с реально работающим `BluetoothHFP`-маршрутом весь звонок.
- После фикса — подтверждено пользователем на реальном устройстве, работает.

**Why:** Bluetooth совпал по времени в первом отчёте чисто случайно — совпадение было принято за корреляцию, пока не появились контрольные тесты, изолирующие переменные по одной.
**How to apply:** Любой `CXProviderDelegate`-метод, читающий/пишущий общее (не per-call) состояние `CallManager`, должен сверяться с `action.callUUID` — CallKit может репортить больше одного `CXCall` за раз (обязательный "must report every push" контракт для дублирующихся/повторных push), и код должен уметь отличить служебный дубль от отслеживаемого звонка. При расследовании "редких" звонковых багов — сначала проверять состояние СОКЕТА звонящего в момент набора (`SKIP not connected`/`watchForStaleConnection` в логе), это чаще реальный триггер, чем совпавшее по времени внешнее условие вроде Bluetooth.

## Известные незакрытые пункты (на будущее)

1. **Нет ручного выбора Bluetooth-маршрута из своего UI** — автоматическая маршрутизация на Bluetooth-гарнитуру/колонку работает (подтверждено, см. Этап 6), но переключиться на неё вручную можно только через нативную кнопку экрана CallKit (до того, как открылся собственный экран приложения) — в `CallOverlay.swift` есть только бинарная кнопка "Динамик" (`toggleSpeaker()`), никакого `AVRoutePickerView`/выбора конкретного устройства из своего UI нет. Предложенный путь: добавить `AVRoutePickerView` в `CallOverlay.swift`.
2. ~~**Экран гаснет при видеозвонках**~~ — исправлено (`ee1fabe`): `CallManager.swift` — `isVideoCall`'s `didSet` выставляет `UIApplication.shared.isIdleTimerDisabled = isVideoCall`, одна точка для всех call site'ов (`enableVideoMidCall()`/`receiveVideoOn()`/`reset()`). Подтверждено пользователем на реальном звонке 2026-08-10.
3. ~~**Звонок иногда "сам отключался" у звонящего**~~ — исправлено (`9ee8708`), см. Этап 6 выше.
